# 第241講 不変条件の監視とサーキットブレーカー

第18部 インフラ運用とデータ・第66章 モニタリングとインシデント対応

[← 第240講](../../part18/lecture240/) | [第18部 目次](../) | [第242講 →](../../part18/lecture242/)

## この講義の問い

デプロイしたあとも不変条件が合っているかどうかは、何で、どれくらいの頻度で確かめるのか。警報が鳴ったら、Marketで何を止められ、何は止められないのか。停止を、誰がどれくらい速くかけられなければならないのか。

## 実習資料

### 準備

第65章の最終バージョン（第53章の最終バージョンのMarket + 運用ツール五つ）に、テスト二つと監視ツール`ops/monitor.py`を加えたバージョンから始める。Marketのコントラクト（`src/`）と`foundry.toml`は第199講のバージョンと同じである。テストにはforge-stdが必要である（`lib/forge-std`）。監視ツールはPythonの標準ライブラリだけを使い、読み取りのリクエストだけを送り、鍵を受け取らない。

デモは、ローカルのanvil一台と、警報を受け取る小さなHTTPサーバー一つで行った。Marketの管理者はマルチシグ（MultiSigAdmin、三人のうち二人）で、上場したトークンは、トークンの持ち主があとから、移すときに引く手数料をオンにできるFeeSwitchTokenである。マルチシグの提案1番（`setStatus(1)`、預け入れの停止）は、a・bが事前に承認だけしておき、実行しない。署名はanvilのデフォルトのテスト用の鍵だけで行った。

### 試すときの注意

- 監視はブロックに入ったものだけを見る。手数料をオンにした取引そのものは警報を出さず、そのあと最初の預け入れが入ったブロックで、すでに足りない状態として捕まる。
- 停止（`setStatus(1)`）は、預け入れ・借り入れ・資産の追加だけを止める。引き出し・返済・清算は止められず、すでにできた不足分も埋められない。
- 事前に承認した提案は、一度実行すれば終わりである。もう一度使うには、新しい提案と承認二つが必要である。
- 同じ警報がブロックごとに鳴り直さないように、監視は新しく崩れたものだけを警報として出し、また合えば解消を出す。
- 監視の生存確認（`--heartbeat`）は、監視とは別の場所で動かす。監視やノードが止まると、警報も止まる。
- 確認したブロックのハッシュと取引のハッシュは、実行するたびに違うことがある。heartbeatの秒は実行するたびに数秒違う。

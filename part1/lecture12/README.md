## この講義の問い

第11講の最後の問い：同じお金を帳簿に違う形で書くと、何が変わるのか。

## 実習資料

### 準備

Foundryの`anvil`（ローカルのテストチェーン）と`cast`だけあればよい。送る側はanvilの既定アカウント0番（`0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`）、受け取る側は1番（`0x70997970C51812dc3A010C7d01b50e0d17dc79C8`）である。署名にはanvilの既定アカウント0番の公開されたテスト用の鍵を使う。

### 実行結果

EOAの四つの欄。`cast balance`（wei単位と`--ether`）、`cast nonce`、`cast proof`の出力：

```
10000000000000000000000
10000.000000000000000000
0
codeHash 0xc5d2...a470, storageHash 0x56e8...b421
```

EOAのcodeHashは空のバイト列のkeccak256と同じである（`cast keccak 0x` → `0xc5d2...a470`）。

`cast send`で1 ETHを一回送ったあと。レシートはstatus 1、gasUsed 21000で、送った側のナンスと二つのアカウントの残高は次のとおり：

```
nonce 1
送った側 9998.999978999999979000
受け取る側 10001.000000000000000000
```

空いた番号。ナンス2と3を先に送ると（`--async`）、アカウントのナンスは1のままで、二件は待ち行列に入る（`cast rpc txpool_status`）：

```
{"pending":"0x0","queued":"0x2"}
```

抜けたナンス1を送ると、詰まっていた2、3がまとめて入ってナンスが4になり、待ち行列が空になる。受け取る側の残高は10004.000000000000000000になる。

```
{"pending":"0x0","queued":"0x0"}
```

すでに過ぎた番号。ナンス4で一件送って成功（status 1）したあと、同じナンス4でもう一度送ると`nonce too low`で拒否される。

コントラクトの四つの欄。デプロイ用バイトコード`0x602a6000556001601160003960016000f300`を`cast send --create`でデプロイすると、コントラクトアドレスは`0x5FC8d32690cc91D4c39d9d3abcBD16989F875707`になる。`cast storage <アドレス> 0`は`0x...2a`、`cast proof <アドレス> 0`は次のとおり：

```
codeHash 0xbc36...c98a, nonce 0x1, storageHash 0x81d1...6861, storageProof value 0x2a
```

codeHashはランタイムコード1バイト（`00`）のkeccak256と同じである（`cast keccak 0x00` → `0xbc36...c98a`）。

デプロイ用バイトコードの読み解き：`60 2a 60 00 55`（ストレージの0番の欄に0x2aを記録） + `60 01 60 11 60 00 39`（17バイト目から1バイトをメモリにコピー） + `60 01 60 00 f3`（その1バイトをランタイムコードとして返す） + `00`（ランタイムコードのSTOP）。

### 試すときの注意

- 最初の送金のあとの送った側の残高（9998.999978999999979000）は、anvilの既定のガス価格によって変わる。
- コントラクトアドレスはデプロイしたアカウントとそのナンスで決まる。上のアドレスは、デプロイしたアカウントのナンスが5のときの値である。

## この講義の問い

初期のイーサリアムの事件はどこで起き、何が直したのか。チェーンの規則と言語が直した事件と、コードを書く人が防がなければならない事件は、どう違うのか。それらの事件は今も起こりうるのか。

## 実習資料

### 準備

リプレイ攻撃をチェーンの規則（EIP-155）が防ぐことを直接確かめる。攻撃コードはなく、チェーン番号の違うanvilのノード二つ（31337、31338）とcastだけを使う。anvilの0番アカウントのテスト用キーで、31337用のlegacy取引（gas 21000、gasPrice 2 gwei、1 ether）を署名だけして（`cast mktx --chain 31337 --legacy`）、同じ内容を31338用にも署名し、`cast decode-transaction`で二つの署名の値vを比べる。次に、31337用の署名済み取引を31338のノードに先に送り（`eth_sendRawTransaction`）、ブロックを一つ作ってからレシート・nonce・残高を見て、同じ取引を31337のノードに送る。anvilのデフォルトのテスト用キーは誰もが知っている値なので、実際の資産には使わない。

### 実行結果

二つの署名のvの値と、31337用の署名を二つのノードに送った結果。`---`の行と各行の前の説明は、castの呼び出しをまとめたシェルが付けた見出し（このシェルは付録に入れていない）である：

```
chain-id A 31337 / B 31338
--- 31337用に署名した取引
  chainId 0x7a69 (31337) nonce 0x0 value 0xde0b6b3a7640000 v 0xf4f5 (62709) hash 0xfd7368dc672482eee7adfd0e8d2bdad7d92592ede85248663298d33d832d3abf
--- 31338用に署名すると
  chainId 0x7a6a (31338) nonce 0x0 value 0xde0b6b3a7640000 v 0xf4f8 (62712) hash 0xcefcd12c46d6a96492899bd556c62fc70937ca9d5a0677754bb984bb194515e5
--- B(31338)に送る
hash 0xfd7368dc672482eee7adfd0e8d2bdad7d92592ede85248663298d33d832d3abf
B receipt null / B nonce 0 / B TO balance 10000000000000000000000
--- A(31337)に送る
A status 0x1 block 1
A nonce 1 / A TO balance 10001000000000000000000
```

31338のノードはハッシュは返すが、ブロックを作ってもレシートがなく、送った側のnonceと受け取る側の残高（10000 ETH）もそのままである。同じ取引が31337のノードでは1番ブロックに入り、受け取る側が10001 ETHになる。

### 試すときの注意

- vの値はEIP-155の式（チェーン番号 × 2 + 35または36）と合う。31337 × 2 + 35 = 62709（0xf4f5）、31338 × 2 + 36 = 62712（0xf4f8）。
- チェーン番号が取引の署名に入るので、取引の署名のリプレイはチェーンの規則が防ぐ。アカウントのコードが直接確かめる署名（コントラクトの中の署名確認）は、チェーン番号を入れるかどうかをコードを書いた人が決める。
- 31338のノードが取引を受け取ってハッシュを返したからといって、ブロックに入ったわけではない。レシートとnonceで確かめる。

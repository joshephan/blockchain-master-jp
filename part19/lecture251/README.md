## この講義の問い

Yulよりもう一層機械の側に降りると、何を直接書くことになるのか。ラベルとスタックだけで書いたコードは、どこで間違えやすいのか。手で書いたバイトコードは本当にいちばん小さく、いちばん安いのか。

## 実習資料

### 準備

同じこと（スロット0に値を書く`setValue(uint256)`、読む`getValue()`）をする四つのバージョンをanvilにデプロイし、サイズとガスを同じ順番で測る。プロジェクトフォルダなしで、solc 0.8.30とFoundryのanvil・castだけを使う。Huffのコンパイラは使っていない。Huffの二つのバージョンは、HuffドキュメントのチュートリアルSimpleStorageのソースの命令を順に手で移したバイトであり、Huffコンパイラの出力とバイトまで同じかは確認していない。

### コード

| ファイル | 内容 |
|---|---|
| [code/huff251/Store251.sol](code/huff251/Store251.sol) | Solidityのバージョン：setValue・getValue、スロット0 |
| [code/huff251/Store251.yul](code/huff251/Store251.yul) | Yulのバージョン：switchのディスパッチャー、defaultでrevert、setValueのあとにstop |

手で移したランタイムのバイト（16進数）：

| バージョン | バイト数 | ランタイム |
|---|---|---|
| ドキュメントのバージョン（SimpleStorageそのまま） | 52 | `60003560e01c8063552410771461001c5780632096525514610023575b6004356000555b60005460005260206000f360006000fd` |
| 直したバージョン（revertの行をラベルの前に、setValueのあとにstop） | 53 | `60003560e01c8063552410771461002157806320965255146100295760006000fd5b600435600055005b60005460005260206000f3` |
| sub_ok（subtract一つ、セレクタの検査なし） | 15 | `6024356004350360005260206000f3` |
| sub_swap（引数を積む順番だけを変えた） | 15 | `6004356024350360005260206000f3` |

デプロイするときは、ランタイムの前に初期化コード9バイト`60{長さ}8060095f395ff3`を付けて`cast send --create`で送る。52バイトのバージョンなら`6034 80 6009 5f 39 5f f3`（PUSH1 0x34、DUP1、PUSH1 0x09、PUSH0、CODECOPY、PUSH0、RETURN）で、自分のコードのうち先頭9バイトのあとの52バイトをメモリ0にコピーして返す。Solidityのバージョンは`solc --via-ir --optimize --optimize-runs 200 --evm-version osaka --bin`、Yulのバージョンは`solc --strict-assembly --optimize --evm-version osaka --bin`でビルドした。

### 実行結果

`cast disassemble`で見たドキュメントのバージョン（左がディスパッチャー、右がsetValueのラベルから最後まで）：

```
00000000: PUSH1 0x00          0000001c: JUMPDEST
00000002: CALLDATALOAD        0000001d: PUSH1 0x04
00000003: PUSH1 0xe0          0000001f: CALLDATALOAD
00000005: SHR                 00000020: PUSH1 0x00
00000006: DUP1                00000022: SSTORE
00000007: PUSH4 0x55241077    00000023: JUMPDEST
0000000c: EQ                  00000024: PUSH1 0x00
0000000d: PUSH2 0x001c        00000026: SLOAD
00000010: JUMPI               00000027: PUSH1 0x00
00000011: DUP1                00000029: MSTORE
00000012: PUSH4 0x20965255    0000002a: PUSH1 0x20
00000017: EQ                  0000002c: PUSH1 0x00
00000018: PUSH2 0x0023        0000002e: RETURN
0000001b: JUMPI               0000002f: PUSH1 0x00
                              00000031: PUSH1 0x00
                              00000033: REVERT
```

セレクタは`cast sig "setValue(uint256)"` → `0x55241077`、`cast sig "getValue()"` → `0x20965255`である。

四つのバージョンを同じ順番（デプロイ → setValue(5) → setValue(7) → getValue）で測った値。デプロイ・setValueはレシートのgasUsed、getValueは`cast estimate`：

| バージョン | ランタイムのバイト | デプロイ | 最初のsetValue（0 → 5） | もう一度setValue（5 → 7） | getValueの見積もり |
|---|---|---|---|---|---|
| Solidity | 150 | 85,847 | 43,461 | 26,361 | 23,311 |
| Yul | 43 | 62,468 | 43,346 | 26,246 | 23,232 |
| ドキュメントのバージョン | 52 | 64,300 | 43,467 | 26,367 | 23,239 |
| 直したバージョン | 53 | 64,504 | 43,348 | 26,248 | 23,239 |

ドキュメントのバージョンと直したバージョンに同じものを送った結果：

| 送ったもの | ドキュメントのバージョン | 直したバージョン |
|---|---|---|
| `cast call setValue(5)`の返り値 | `0x00…05`（SET_VALUEの下のGET_VALUEが続けて動く） | `0x` |
| セレクタ`0xdeadbeef` + 9 | 成功（gasUsed 26,389）、保存値9 | 巻き戻し、保存値7のまま |
| 空のcalldata + 1 wei | 成功（gasUsed 21,385）、保存値0、残高1 | 巻き戻し |
| setValue(3) + 1 wei | 成功、残高2 | 成功、残高1 |

Solidityのバージョンは上の三つ（知らないセレクタ、空のcalldata + 1 wei、setValue(3) + 1 wei）をすべて巻き戻す。Yulのバージョンは前の二つを巻き戻し、setValue(3) + 1 weiは受け取る。

subtractの二つのバージョンに`subtract(7,3)`を送った結果（どちらもデプロイgasUsed 56,384、どちらも成功）：

```
sub_ok subtract(7,3) -> 4
sub_swap subtract(7,3) -> 115792089237316195423570985008687907853269984665640564039457584007913129639932
```

sub_swapはSUBの直前のスタックが[3, 7]なので、3 − 7が2の256乗 − 4に回り込む。

### 試すときの注意

- ラベルはジャンプしてくる場所を示すだけである。止める命令（`stop`、`return`、`revert`）を書かなければ、その下のコードが続けて動く。ドキュメントのバージョンの最後の`0x00 0x00 revert`には、どの道からもたどり着かない。
- バイトを手で移すと、一つ抜けただけで後ろのラベルの位置が全部ずれる。ディスパッチャー28バイト（0x00〜0x1b）のあとのsetValueのラベルが0x1c、その本体7バイトのあとのgetValueのラベルが0x23である。直したバージョンでは0x21、0x29に変わる。
- 直したバージョンにも値の検査（`callvalue`）と引数の長さの検査はない。
- Solidityのバージョンの150バイトのうち、最後の53バイトはメタデータの尾（`a264…0033`）である。
- 最初のsetValueの大部分は、0から値へ書くSSTORE 1回（22,100）である。四つのバージョンの最初のsetValueの差は、いちばん大きいものと小さいもので121である。

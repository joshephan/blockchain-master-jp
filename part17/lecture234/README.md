## この講義の問い

大きな計算をやり直さずに、合っているかどうかをどう確かめるのか。「ゼロ知識」は何を隠し、ZKロールアップはそのうち何を使うのか。証明を確認するコントラクトは実際に何の計算をし、その計算は誰が決めるのか。

## 実習資料

### 準備

二つを使う。ZKの回路や制約言語のコードはない。

- `python/poly234.py`：大きな計算をやり直さずに、ランダムな一点で確かめる算数。Pythonの標準ライブラリ（random、time）だけを使い、乱数のシードは234である。
- `rollup`：第232講と同じ講義用のFoundryプロジェクトで、講義用の証明確認コントラクト`Schnorr234`（「pub = x·Gであるxを知っている」をxなしで確認）とそのテストを使う。曲線はalt_bn128で、プリコンパイル0x06（加算）・0x07（乗算）を呼ぶ。依存関係はforge-std 1.17.0である。同じ確認をanvil（`--hardfork osaka`）にデプロイしてcastでもう一度実行した。外部のチェーンには接続しない。

証明を作る（テストとanvilの流れが同じ順番で計算）：

```
x = 0x5ec2e7            証明する側だけが知っている数
pub = x·G               公開値（曲線上の点）、mul([1,2], x)
k = 0x7a11d0            1回使って捨てる数
R = k·G                 mul([1,2], k)
c = challenge(pub, R, keccak256("batch 7"))
s = k + c·x  (mod N)
```

証明は(R, s)である。式が合う理由は、s·G = (k + c·x)·G = R + c·pubだからである。G = (1, 2)はalt_bn128曲線の生成点である。

### 試すときの注意

- `verify`1回は、0x07の乗算2回と0x06の加算1回である。xが大きくても小さくても、確認の値段はほとんど同じである。
- 問う数cにチェーン番号と確認コントラクトのアドレスを入れたので、ほかのチェーンやほかの確認コントラクトでは同じ証明は通らない。公開入力に入れなかった値については、証明は何も教えてくれない。
- 問う数を証明する側が選んではいけない。だから、Rを先に決めないとcが出てこない順番で作る。
- 二つの多項式が違えば、同じ値が出る点は多くても次数の分だけで、選べる点は約2^253個なので、ランダムな一点の確認は間違った結果をほとんど見逃さない。
- `Schnorr234`は講義用の確認コントラクトである。実際のZKロールアップの確認コントラクトは、証明の値をいくつかと公開入力をいくつか受け取り、定数として入れておいた確認鍵で、決めておいた式一つを計算する（曲線を使う方式ならペアリングのプリコンパイル0x08）。

## 時効性のあるデータ

基準日時点の値。証明方式は名前と準備が要るかどうかだけを書いた。証明の大きさ・確認の値段・証明する側の機材は実装ごとに違い、変わるので載せない。

| 項目 | 値 | 基準日 |
|---|---|---|
| Foundry（forge・cast・anvil） | 1.8.3、commit cae51ad4 | 2026-10-21 |
| solc | 0.8.30 | 2026-10-21 |
| python | 標準ライブラリのみ（random、time）、乱数のシード234 | 2026-10-21 |
| 証明方式の名前（例） | Groth16（回路ごとに1回行う準備）、PLONK（複数の回路が共通で使う準備）、STARK（準備なし） | 2026-10-21 |
| イーサリアムのKZG信頼設定のセレモニー | あった（日付は載せない） | 2026-10-21 |
| EIP-1108のペアリングのガス | 45,000 + 34,000 × ペアの数 | 2026-10-21 |
